## Source-backed constraints to resolve deliberately

- `dependencies.ts` currently includes global registryRevision in every v5/v6
  dependency hash. Any binding update therefore invalidates unrelated proposals.
  Merely calling existing POST/jobs(cableIds) does not solve scoped currentness.
- `recalculationSchema.ts` emits global dirty generations for endpoint mutations;
  `recalculationRepository.ts` supersedes global enrollments and has a finite
  current-login authority (30minutes or earlier login expiry). Do not pretend
  a calculation-only LevelB grant permits a cable write.
- `jobs.ts`, `worker.ts`, `apply.ts`, `routingScope.ts`, endpoint/comparison
  provenance guards, revision envelopes and U1 proof reader must agree on the
  versioned dependency contract. Old v5/v6 results retain strict old semantics;
  never ignore arbitrary fields in their existing hashes.
- U1 still requires a completed parent job for Review-ready display. For a new
  explicitly versioned scoped flow, a successfully sealed completed cable item
  should become independently reviewable while sibling items wait. Retain
  cancellation/failure/current-authority checks and exact current dependencies;
  never promote waiting/blocked items or unsealed partial output. Any relaxation
  must be version-specific across server Review/Apply and client schemas, with
  historical whole-job behavior preserved unless equivalently proven.
- Existing workerScheduling uses bounded fair per-project calculation slices;
  reuse it. Do not add parallel engine processes or silently rebuild/relabel
  admitted engine identity. Measure waiting/admission/engine/read phases before
  claiming a speedup. U1 page proofs remain bounded, not a throughput guarantee.
