# Stage 0 design: offline companion-material recommendations

## 1. Scope, evidence and decisions

**Stage 0 only.** This document specifies a catalog-wide framework and two initial adapters: bolt to washer/nut, and cable/cable type to marker. It does not implement recommendations or certify any engineering rule. Reviewed checkout: WFC, branch `AI-suggestion-implementation`, commit `96bcb58827c15ea738933f3adc3fcead837aff11`, 2026-09-12. The initial working tree was clean. Remote identity is `https://github.com/MrToKa/WFC.git`; the read-only remote probe failed, so this is a local-checkout audit. No database connection, application startup, migration, real-data inspection, training or dependency installation was performed. The user's prohibition on database changes applies throughout this run.

**Observed** means supported by the cited source or executed check. **Proposed** means future functionality. **Unverified** means source inspection cannot establish the fact. References use `repository/path:line` and symbol names, anchored to the revision above. Executed checks and S01–S22 design cases are in [STAGE_00_VERIFICATION.md](STAGE_00_VERIFICATION.md); implementation dependencies are in [STAGE_01_HANDOFF.md](STAGE_01_HANDOFF.md).

Decision: preserve the existing seven-category composition infrastructure and explicit owner foreign keys. Add stable identity/metadata, occurrence allocations, revision/review evidence and backend rule adapters around it. Do not introduce a second material catalog, infer compatibility from names, automatically approve historical rows, or use ML to define mandatory roles. Future categories share the protocol but remain `unsupported-category` until enabled reviewed rules and required attributes exist.

## 3. Current flows, invariants and gaps

### 3.1 Catalog open and composition edits

`MasterMaterialDetailsPage.loadDetails` calls `src/api/materials.ts:71`, `fetchMaterialDetails`, then the category route returns material plus assignments. Shared `StandardMaterialsSection` is rendered at `src/pages/Materials/MasterMaterialDetailsPage.tsx:237`; the recommendation panel belongs beside it. Category wrappers retain their existing detail properties.

`src/pages/Materials/MasterMaterialDetailsPage.tsx:155`, save handler, invokes create/update API functions (`src/api/materials.ts:78`, `createStandardMaterial`; `:91`, `updateStandardMaterial`). `src/pages/Materials/components/StandardMaterialDialog.tsx:116` submits child UUID, quantity, unit and remarks; purpose is a catalog filter, not a semantic role. Existing UI edits are admin-gated (`src/pages/Materials/MasterMaterialDetailsPage.tsx:67`); server mutations independently enforce `authenticate` and `requireAdmin` (`server/routes/standardMaterialRoutes.ts:55`, `registerStandardMaterialMutationRoutes`). `requireAdmin` rechecks database user status (`server/middleware.ts:28`). Catalog GET routes have no global authentication middleware (`server/app.ts:36`; `server/routes/installationMaterialCatalogRoutes.ts:649`). Do not claim that current public lists already provide scoped, approved candidate retrieval.

`server/models/standardMaterial.ts:1` defines seven owner categories, three child categories and `pcs | meters | pcs/m`. `server/services/standardMaterialService.ts:360`, create, `:388`, update, and `:441`, delete, run through transactional route callers. `assertAssignmentValid` checks owner/reference existence, self-link, duplicate and graph cycles; explicit assignment tables have owner/child foreign keys, uniqueness and positive finite quantity constraints (`server/db.ts:428`, assignment definitions; additional tables later in the same initializer). Owner deletion cascades only its composition; referenced-child deletion is restricted.

`server/services/standardMaterialService.ts:267`, `expandStandardMaterialsFromAssignments`, multiplies quantities along paths and uses a path-local traversal stack, allowing the same child in independent branches while rejecting actual cycles. `aggregateExpandedStandardMaterials` (`:160`) groups expanded material/category/unit/normalized remarks and loses occurrence/allocation detail. Units are carried from children; there is no general dimensional conversion. No role, position or packaging semantics can be inferred from that multiplication.

**Gaps:** no revision precondition, acceptance idempotency or whole-graph serialization. Two graph edits can pass cycle checks against stale graphs; read/merge/update can overwrite another edit. Existing duplicate owner+child constraints do not represent multiple role/position allocations. Keep them for legacy aggregate edges and add an allocation sidecar; do not weaken them just to store duplicates.

### 3.2 Project/cable inheritance and customization

`server/services/projectCableTypeSnapshotService.ts:5`, `snapshotStandardMaterialsToProjectCableType`, expands master composition and copies name/quantity/unit/remarks, source master material ID and assignment IDs into `cable_type_default_materials`. `replaceInherited` removes only `source_kind='standard-material'` (`:11`), preserving manual defaults. `server/routes/cableTypesRoutes.ts:679` replaces inherited defaults when the source master cable type changes. `src/pages/CableTypeDetails.tsx:353`, loader, and `:499`, edit path, use project cable-type APIs; these are a second integration context, not a new recommendation engine.

Therefore `source_master_material_id` is lineage evidence, not unconditional proof of current selected identity. Current identity and original lineage must be distinct fields; ambiguous rows stay unresolved.

`src/pages/CableDetails.tsx:525`, loader, calls the cable details API. `server/routes/cablesRoutes.ts:2720`, details GET, opens a transaction (`:2745`) and invokes `ensureCableMaterialsInitialized` (`:2755`, helper `:1413`), which can call `resetCableMaterialsToCableTypeDefaults` (`:1373`, DELETE; `:1382`, INSERT; `:1407`, flag update). **Opening this existing detail route can write.** Proposed preview must use a pure reader that virtually overlays defaults if initialization is absent, without setting flags or materializing rows.

Cable add/sync/edit are authenticated (`server/routes/cablesRoutes.ts:2790`, `:2864`, `:2986`). `findProjectCableById` (`:831`) constrains object to project; `ensureProjectExists` (`server/services/projectService.ts:5`) checks existence, not user membership. No per-user project ACL/reviewer permission system was established. Current cable material records are row UUIDs and name-based data; adds insert new UUIDs without role-level reconciliation. ### 3.3 Quantity reports and Change Orders

`server/routes/cablesRoutes.ts:1903`, `buildCableReportSummary`, reads stored rows or virtual defaults for an uninitialized/noncustomized-empty cable (`:1938`). `:1819` multiplies `pcs/m` by cable design length once and reports `pcs`; fixed `pcs`/`meters` are retained. Missing name/unit/quantity and missing length are counted as incomplete (`:1810`, `:1822`). Aggregation is lowercased name+output unit (`:1831`), so report totals do not prove stable identity or role satisfaction.

`server/services/changeOrderService.ts:63`, `calculateInheritedChangeOrderQuantities`, distinguishes a cable-type row (one cable line with commercial length) from piece-based parents. Fixed companions on a cable line are copied once; rate companions follow length. Other parent quantities multiply the per-parent quantity. `:105`, `calculateMinimumOrder`, separates order quantity from package count (`ceil(order/minimum)`). Packaging is a procurement boundary, never a multiplier in role deficit calculation.

`addChangeOrderItem` (`server/services/changeOrderService.ts:503`) expands and copies standard material snapshots (`:539`, `:549`), which prevents live composition edits from automatically re-expanding old child rows. **This does not make all historical values immutable.** `getChangeOrder` (`:305`) calls `synchronizeChangeOrderMaterialOrdering` (`:330`; helper `:157`, UPDATE `:225`), refreshing commercial fields from current catalog rows. Detail/export reads can therefore mutate historical order/packaging fields. The ADR's broad historical statement (`docs/adr/0001-standard-material-composition.md:31`) needs this qualification; the ADR is preserved, not silently overwritten by this audit.

Proposed revisioned templates must not invoke current synchronization on old instances or Change Orders. Freeze new recommendation-linked revisions and report inputs, and put historical refresh behind a separately authorized explicit revision operation. Existing report arithmetic and commercial display must be characterized before a future repair; Stage 0 makes no repair. Cable version history must not be treated as an immutable reviewed-material snapshot: reviews require their own complete component/context snapshots.

### 4.1 Minimal vocabulary and persistence ownership

All types/tables in this section are **proposed**. WFC owns them; Python has no database credentials.

Enforce exactly one non-null FK, category-to-column correspondence and uniqueness of each concrete FK. Metadata/allocation references point to this bridge ID; API MaterialKey remains category+concrete UUID. Record graph occurrence paths before aggregation; path keys include assignment IDs and parent occurrence, not just material ID. A copied occurrence can map to one physical allocation only once; separately instantiated paths are separate occurrences even if identity repeats.

### 4.2 Applicability, quantity and compatibility precede ranking

Pipeline owner: a proposed `materialRecommendationService` in WFC.

1. Resolve subject identity and authorized context; load enabled reviewed rule revisions. Unsupported category/subtype is explicit.
2. Emit all applicable role/position slots with `applicability = required | optional | not-applicable | undetermined`. Preserve the role even if zero eligible candidates exist.
3. Evaluate known requirements and reconcile existing compatible allocations by role+position+occurrence. Record uncertain existing identity/quantity as a blocker, not zero.
4. Retrieve only authorized, approved and available catalog candidates through the existing capability's child catalog. Authorization/catalog filtering occurs before features leave WFC.
5. Apply typed compatibility and whole-assembly constraints. Outcomes are `eligible | ineligible | insufficient-data`, with stable reason codes and missing fields. Ineligible/unknown rows are not actionable candidates.
6. Rank eligible alternatives only. Ranker failure selects a deterministic backend order; it cannot change applicability, quantity or approval.
7. On acceptance repeat steps 1–5 inside the mutation/concurrency boundary using current state. Never trust displayed compatibility or client-supplied scope, deficit or score.

Quantity value: decimal string + canonical unit (`pcs` or `meters`) and `state: known | unknown`; unknown has `value:null` and reason. The legacy `pcs/m` is a **rate**, represented separately as `{value, numeratorUnit:'pcs', denominatorUnit:'meters'}` until multiplied by known length. Require explicit quantity basis `per-parent | per-position | per-length | fixed-assembly`. Do not silently reinterpret a legacy mixed-unit nested composition; ambiguous dimensional paths require review.

For known requirement R and effective compatible allocated quantity E in the same unit/position, `deficit=max(R-E,0)`, `overage=max(E-R,0)`. `satisfaction = missing | partial | satisfied | overage | unknown | not-applicable`. R unknown implies deficit unknown. E incomplete also makes deficit unknown. An optional role with no reviewed chosen quantity has unknown quantity; an optional role explicitly chosen may have a known quantity target without becoming engineering-required. `not-applicable` carries no actionable quantity and flags any existing allocation for human review, without deleting it.

Synthetic S05: reviewed **fixture only** specifies two washers per bolt, four bolts at position P, six eligible washers allocated to P: R=8 pcs, E=6 pcs, deficit=2 pcs. One explicit top-up of two is offered. A box size of 100 has no effect here. Quantity rates are normalized once at the adapter boundary; write an absolute amount or a clearly marked legacy rate, never both an expanded amount and a multiplier. Report adapters must have tests proving no second multiplication. Integer pieces/rate-derived rounding require a reviewed rule (`roundingPolicy`); absent policy leaves nonintegral physical piece requirements unresolved. Procurement rounding remains separate.

### 4.3 Initial engineering adapters and limits

**Fastener adapter.** Typed subtypes `bolt`, `nut`, `washer`; candidate child catalog from the owner capability. A reviewed relation may enable washer and nut roles independently. Nut compatibility may require thread family/standard, nominal size, pitch, handedness, fit/tolerance and material/property/coating combinations. Washer compatibility may require verified inner/outer geometry, thickness, type and bearing interface. Which fields are mandatory is defined by the reviewed rule/application class, not a hardcoded universal engineering checklist. Whole-assembly rules may require grip/stack, available threaded engagement, fastening arrangement, space or approved material pairing. Missing a required field yields `insufficient-data`. No numeric engineering limits or production fixture approvals are invented here.

**Cable-marker adapter.** Subject is verified catalog cable type or a cable with a resolved stable source identity. Marker subtype in the capability's child catalog needs manufacturer-supported mounting style, fit range and applicable marking/environment attributes. Context distinguishes end/route/other positions and count-per-cable versus count-per-length; two markers per cable is not an assumed universal rule. Cable outer diameter alone does not establish marking suitability. Cable length is requested only for rate/spacing rules; end counts/positions only when the rule needs them. Same shared role/quantity pipeline, different attribute and whole-assembly predicates.

All fixture limits and sample IDs below are synthetic control-flow examples. Production enabling depends on a domain reviewer providing evidence and values. Ferrules, ties, glands, supports and other categories remain unsupported for recommendations until their own typed attributes, relations and rule versions are reviewed.

## 5. UI and target semantics

Use the application's English UI language. Add **Recommended companion materials** beside **Standard Materials** on the shared master page and the cable/project cable-type detail contexts. Reuse one panel with a context adapter. Group washers and nuts into separate role/position sections; several nuts are alternatives, never a mandatory bundle. Show applicability, known quantity/deficit, missing data and reasons before candidate ranking. No-candidate, unsupported and undetermined states are distinct; keep the existing manual catalog workflow.

- **Add to this assembly** requires an explicit writable target and position. If none exists, select a project and existing assembly or explicitly create a working assembly. Catalog opening/selection creates no persistent draft. Preview displays per-parent information or unknown totals until count/context is supplied.
- **Top up by …** is an explicit addition/adjustment with old/new amounts. Fully satisfied roles have no add action. Existing manual/inherited rows, overages and conflicts remain visible. Adjustments identify exactly which row/allocation changes and preserve its original provenance.
- **Save as standard assembly** requires shared catalog/template permission, an identified owner, reviewed-compatible child catalog and an explicit new template or new revision choice. The user confirms its quantity basis and preview: S05's eight washers for four bolts becomes two washers per parent, not eight per bolt. Convert absolute instance amounts exactly once into the declared per-parent/per-position/per-length basis; unknown denominators, mixed nonrepresentable bases or missing rounding policy block the save. Persist required application/position context and show the converted composition before submission. It saves composition, not engineering approval; it never rewrites existing project instances.
- **This assembly is reviewed** states the exact revision, roles/positions/application scope and candidate/quantity judgments. An add or template save does not call review automatically.
- **Reject candidate**, **Role not needed**, **Adjust quantity**, **Correct review**, and **Withdraw review** require a reason appropriate to the event. Candidate preference/rejection and role applicability judgments are separate. An ignored suggestion is no judgment.

The legacy cable detail page itself can still write while loading. A future recommendation integration must split this initialization into an explicit mutation and use the pure projection reader, so adding a read-only panel does not hide existing write side effects. Review/learning data must reflect the exact saved revision, never a live mutable projection.

## 6. Proposed API and consistency contract

### 6.1 Shared conventions and authorization

Use existing Express `/api` routes, bearer session authentication, camelCase JSON and `{error: string}` error style, extended with `code` and structured `details`. Every route below is **new/proposed**. Authentication is required even though some legacy catalog GETs are public. Backend derives `scopeKey` and permitted evidence scopes; request body scope is never trusted.

Proposed capabilities are `catalog:read`, `project:read`, `project:write`, `assembly:review`, `catalog:write`, `template:write`, `rule:approve` and scoped internal service permissions. Current admin status can implement shared catalog/template writes initially. Project read/write must explicitly preserve a documented all-authenticated-project policy or implement restricted membership after the deployment owner chooses policy; do not invent memberships. For each target, apply the stricter existing mutation permission too: a project cable-type default still requires admin, while a cable-instance write requires authenticated project-write permission. The generic assembly route cannot bypass the adapter's existing permission. Until policy is recorded, restricted-scope rollout and evidence export are blocked. Reviewer/domain-approver assignments are also required inputs, not inferred from successful login. No ranker endpoint authorizes user mutations.

`...` in the table expands to `/api/projects/:projectId`; it is not a literal endpoint. Reader preference feedback remains unreviewed and excluded from both similarity and training until an authorized reviewer incorporates it into an explicit reviewed snapshot/judgment. Detailed internal read/delta protocol: ranker obtains only signed scope grants from WFC, then `GET /api/internal/material-recommendations/evidence?afterGeneration=...` returns allowed immutable review deltas plus withdrawal tombstones. Export endpoints cannot select arbitrary user-supplied scopes. Both endpoints audit scope and exclude drafts/unreviewed/out-of-scope data.

Common mutation envelope: `expectedAssemblyRevision` where assembly-affecting, `expectedVersions:{catalog,rules,feature}`, and `idempotencyKey`. Review corrections use `expectedReviewEventVersion`; template writes additionally use `expectedTemplateRevision` (`null` for create). A scoped DB receipt uniquely keys `(actor, operation, target, idempotencyKey)`, stores canonical request hash and result in the same transaction. Exact retries return the receipt (even if the current revision advanced); different payloads return 409. Concurrent distinct keys serialize on assembly/template head; loser observes a revision conflict, not a second add.

Publishing a project composition or application context into a broader template scope additionally requires an explicit `scope:publish-template` grant for that source/destination pair. Source read and shared-catalog admin rights alone do not authorize disclosure. Deny scope widening while policy/grants are absent; alternatively save a template restricted to the source scope if its template-write policy permits it. The saved snapshot includes only approved-to-publish fields; retain restricted lineage references without exposing private project names/context to other readers. Ranker grants never supply this user permission.

All write success bodies include `schemaVersion:'recommendations.v1'`, `requestId` and `receiptId`. The following fields complete each operation's output contract; replay returns the same committed body. Status codes are 201 for a newly created domain resource/event, 200 for a committed adjustment/acceptance or replay, and 202 for an export job queued rather than finished.

| Review correction / withdrawal | `reviewId`, `reviewEventId`, `reviewEventVersion`, `reviewStatus:'corrected'` or `'withdrawn'`, `replacementReviewId` (null for withdrawal), `evidenceGeneration`, `dependentArtifactsStatus:'disqualified'`; the dependency registry and generation are committed before reply |

Proposed `GET /api/internal/material-recommendations/exports/:exportJobId` requires the same currently valid service scope grant and is read-only; returns `{schemaVersion,requestId,exportJobId,exportStatus:'queued'|'running'|'ready'|'failed'|'revoked',dataVersion,featureVersion,evidenceGeneration,scopeKey,manifest,artifactHandle,error}`. Manifest/handle are null until ready; manifest includes hashes, review/lineage dependencies, split-independent record counts and cutoff. Artifact handle is an opaque local scoped identifier, never a client-supplied filesystem path; download/access rechecks scope. Error is null except failed/revoked jobs. Creating an export uses `idempotencyKey` and frozen cutoff/generation; it does not advance the reviewed evidence generation.

Evidence delta success is `{schemaVersion,requestId,scopeKey,fromGeneration,toGeneration,featureVersion,reviews:[{reviewId,reviewEventVersion,snapshotHash,lineageRootId,coveredScope,features,judgments}],tombstones:[{reviewId,reviewEventVersion,generation,reasonCode}],nextCursor,hasMore}`. Cursor is opaque and bound to scope/feature version/frozen toGeneration; final page has nextCursor null. Consumers apply pages atomically as a generation, never activate a partial delta. An expired cursor returns 409 with `code:'evidence-resync-required'`; revoked grant returns 403 and unusable local evidence, not an empty success. This GET has no domain writes.

Lock the mutable assembly head and relevant catalog/rule generation records, recheck versions, then validate and write atomically. All legacy writes touching protected rows must participate in revision invalidation/locking before recommendation mutations ship. Serialize composition graph mutation per child-catalog graph (consistent lock order) so concurrent cross-links cannot evade cycle checks. A bounded retry may handle serialization failure, but never auto-rebase a stale user acceptance. No DB uniqueness constraint alone can replace role/position reconciliation.

### 6.3 Ranker, normalization, caching and failure

Proposed `POST /v1/rank` internal FastAPI service request: `{requestId, scopeGrant, schemaVersion, featureVersion, rulesVersion, evidenceGeneration, candidateSetHash, subjectFeatures, contextFeatures, roles:[{roleKey,positionKey,candidates:[{material,features}]}]}`. Response: `{requestId,scopeKey,schemaVersion,featureVersion,rulesVersion,evidenceGeneration,indexVersion,modelVersion,trainingDataVersion,candidateSetHash,roles:[{roleKey,positionKey,rankingMode,modelVersion,orderedMaterialKeys:[...]}]}`. Each output list must be an exact permutation of the submitted role's eligible candidates. Reject invented/duplicate/missing IDs, cross-role leakage, nonfinite scores if present, version/scope/hash mismatch, oversized payload, invalid JSON or timeout. WFC recomputes reasons and quantities; Python returns no write instructions or approvals. `evidenceGeneration` denotes current live index/tombstone state; immutable model `trainingDataVersion` may be older if still qualified. A new positive review updates similarity without automatically invalidating a valid classifier; revocation checks still apply to its dependencies. Return per-role ranking modes/model versions when the release maps some roles to baseline, and top-level `ranking.mode='mixed'` if needed.

Use one versioned backend feature builder for both scoring and exports: `materialRecommendationFeatures.ts` (proposed). `features.v1` defines canonical units, explicit missing masks, typed subtype/context fields, allowed categorical values, no free-text identifiers as compatibility features, and no outcome/review fields in prediction inputs. Export and online scoring use identical canonical JSON schema and fixture vectors. Any learned encoding/scaling lives in the same pinned Python pipeline artifact used by train and serve; fit it on training partitions only. This follows the consistency/leakage guidance in [scikit-learn common pitfalls](https://scikit-learn.org/stable/common_pitfalls.html). Normalization version changes invalidate incompatible indexes/models; no ad hoc Python reinterpretation of units.

Proposed operational starting limits, **not measured performance claims or engineering thresholds**: 256 KiB rank payload, at most 32 role/position groups and 100 eligible candidates per group per call, 300 ms rank timeout, no retry on the interactive request, three consecutive failures open a 30-second circuit. Split larger results into deterministic bounded pages and show total eligible count/truncation. Do not drop role status or falsely claim no candidates when the backend search is incomplete; mark `candidate-search-incomplete` and continue manual/paged retrieval. Assembly graph traversal has explicit depth/node/request budgets; exhaustion produces `insufficient-data` and no acceptance, never a silently partial quantity total. Final load-test budgets are set during pilot.

Fallback is a backend stable sort by reviewed rule priority (where provided), normalized display label, then category+UUID; only eligible candidates participate. No second complex similarity engine in WFC. Return `ranking.mode='deterministic'` and a reason (`disabled`, `unavailable`, `invalid-response`, `evidence-stale`, `no-reviewed-examples`). Rule/quantity results still work if Python is absent. Python service `healthy` is not a prerequisite for WFC startup or WFC's core health endpoint.

In-memory cache keys include authorized scope/permission generation, subject identity+metadata revision, context/positions+basis, assembly revision, catalog/rules/feature versions, evidence generation, index/model and pagination. Never cache by name or subject alone. Catalog edits/approval revocation, assembly edits, template revision changes, rule updates, review/correction/withdrawal, scope grants/revocations and activation events invalidate affected keys. Backend checks generations before returning cached results. If ranker has not applied the current evidence/tombstones, skip its response and use deterministic fallback; do not serve withdrawn evidence during index lag. Preview may fill volatile caches, but writes no domain/audit draft rows.

## 7. Reviewed evidence and local learning

### 7.1 Lifecycle, labels and immediate benefit

Draft/current assembly → explicit immutable review of a named revision/scope → active evidence only for that reviewed revision. A relevant edit makes the current revision unreviewed; it does not rewrite or automatically invalidate an otherwise correct historical review. A correction or withdrawal explicitly disqualifies affected evidence. Relevant edits include components, allocations, quantities, applicability context and metadata/rule basis. Store review reasons, reviewer authorization, source/template lineage, whether model suggestions were shown, accepted/modified suggestions and original model/index versions.

Review judgments separate: (a) role applicability, (b) quantity correctness, (c) hard candidate incompatibility, and (d) preference among already eligible candidates. Hard incompatibility is a rules/data-quality signal for review, not a shortcut for the ranker to learn engineering safety. Positive preference means explicitly judged suitable/preferred in this context. A negative preference requires an explicit contextual judgment; selecting A does not label every unseen B negative. Absence, ignored suggestions, missing catalog alternatives and an unreviewed add are unlabeled. Quantity adjustments are not candidate rejection. `role-not-needed` never means all candidates for that role are globally unsuitable.

Similarity baseline in Python: use enabled-role, schema-compatible, authorized positive reviewed examples. Filter comparable subtype/application/basis, compute deterministic weighted typed-feature similarity with missing fields excluded (never manufacture known attributes), and score each submitted candidate by lineage-capped support among matching reviews. Weights and tie-break are versioned configuration, initially simple equal weights over reviewed comparable features; engineering eligibility is already decided by WFC. If no comparable examples exist, return stable deterministic order. Maintain one latest valid contribution per reviewed lineage/context/role judgment; one hundred copies count as one lineage, not 100. Independent manually engineered instances can have distinct roots with recorded origin evidence; cannot self-declare independence merely by copying/renaming.

Review commit increments scope evidence generation and emits an outbox/delta event in the same transaction. Ranker incrementally updates its scoped index without retraining; the next response using that generation benefits from the new review. If update is delayed, backend stays useful with fallback and reports evidence lag. No classifier is needed for this path.

### 7.2 Training, evaluation and promotion

Later CPU-only candidate: logistic regression over normalized subject/context/candidate features, trained only for roles with adequate independent explicit positive and negative **preference** judgments. Use it as a ranking score, not calibrated engineering confidence. Positive-only sets can operate the similarity baseline indefinitely; training returns `skipped-insufficient-labels` instead of synthesizing negatives. Manual, inherited and model-assisted provenance are separately measured; model-assisted examples do not constitute independent evaluation proof by default.

1. Local scheduled trainer requests a WFC-generated immutable scoped export at a cutoff. Manifest includes review IDs/versions, lineage groups, scope/permission generation, catalog/rule/feature versions, all tombstones, label semantics, eligibility candidate sets and content hashes. Backend controls access; trainer does not query Postgres.
2. Deduplicate lineages; count independent *new* judgments since last evaluated data version. Check per-role independent groups, class/judgment coverage, missingness, applicability coverage and candidate-set coverage. Record attempted version even when skipping; do not advance evaluated or active version.
3. Acquire a single-writer scope training lease and train out of process within CPU/RAM limits. Serving retains its current artifacts. Persist seed, software/image digest, feature pipeline and split manifest.
4. Group by entire connected lineage, using temporal holdout of later independently reviewed cases. Keep tuning/validation and final holdout distinct. Remove held-out lineages from both model fitting and similarity frequencies/index used in evaluation, including historical copies. Evaluate incumbent only on cases not used by its own dependency manifest; if clean common cases are unavailable, promotion is underpowered and skipped.
5. Compare candidate, valid incumbent and similarity baseline on identical authorized eligible candidate sets and judged cases. Report role coverage and retrieval/candidate coverage separately from ranking. Proposed primary metric: macro per-role NDCG@k, with k predefined; a ranking evaluation case qualifies only when every candidate in its frozen eligible evaluation set has an explicit relevance judgment and at least one is relevant. Any unjudged candidate makes that case incomplete and excluded from the primary promotion metric; report the exclusion and judgment coverage, never assign it zero relevance. Fully judged all-negative cases are measured separately for candidate coverage/abstention, not assigned an artificial NDCG value. Also report quantity/rule correctness (deterministic, no regression tolerated), missing-role rate, latency and memory. Never let a better ranking score hide poor candidate coverage.
6. A versioned gate configuration is required before auto-promotion: enabled roles, independent new/total group minima per role, positive/negative judgment minima, candidate judgment coverage, primary metric+k, minimum meaningful gain against both incumbent and baseline, uncertainty method/confidence criterion (group-level resampling), per-role regression limits, deterministic correctness requirements and p95 latency/RAM targets. Numeric quality thresholds are **unset in Stage 0**. Pilot domain review and measured independent data establish them, then freeze them before evaluating a candidate. Missing settings, tied/inconclusive results, empty role slices or insufficient power block promotion.
7. Require all enabled supported-role gates to pass. A candidate with aggregate gain but role regression does not activate. Unsupported/unqualified roles keep their explicitly recorded baseline mapping. Initial rollout uses an all-or-nothing release for the configured supported role set, avoiding hidden selective success reporting.
8. Write candidate artifacts to staging, validate hashes/schema/scope/dependencies, complete evaluation, load-test and mark ready. Atomic active-manifest compare-and-swap is conditioned on unchanged active/evidence/permission generations. Serving loads/warms immutable artifacts before acknowledging activation. On interrupted/failed activation keep last compatible **qualified** release or baseline; never select a half-written directory.

Use a local daily schedule as an operational default with UTC timestamping (configurable); no Codex scheduled automation. On restart perform at most one overdue catch-up check, not a backlog of training jobs. Lease includes owner token, heartbeat and expiry; stale recovery requires expiry, absence of a valid owner and atomic takeover. Bound transient export/job retries (proposed three with backoff), do not retry invalid-data/quality skips until evidence/config changes. Persist `attemptedDataVersion`, `evaluatedDataVersion`, `activeDataVersion`, job state and reason separately. Failed jobs release/expire leases and leave serving unchanged.

### 7.3 Withdrawal, revoked scope and rollback

Correction/withdrawal increments evidence generation, invalidates live caches/index entries and records a permanent tombstone. Maintain reverse dependency manifests for indexes, trained artifacts, evaluation evidence and scope grants. If revoked/erroneous evidence affected fitting **or promotion evidence**, immediately disqualify dependent releases and active mappings; merely excluding it from the next export is insufficient. Select the last compatible artifact with no disqualified dependencies, or scoped positive similarity rebuilt without it, or deterministic fallback. Keep a durable disqualification registry that rollback and restore must consult.

Scope revocation also removes affected data exports/index partitions from serving/trainer access and prevents cached cross-scope responses. Backend authorization is checked anew, not delegated to an old artifact grant. Retraining from clean data can produce a new candidate; it must pass current gates again. Historical immutable review events remain restricted audit records under retention policy; removal from learning does not erase history. Backup restore reapplies the latest permission/tombstone registry before any artifact can be served.

## 8. Deployment, offline operation and storage

Proposed minimal addition: one pinned CPU Python/FastAPI image used for `ranker` and an optional `trainer` profile/process, a private WFC-to-ranker route, and a local artifact volume. No GPU reservation, CUDA, LLM, public inference service or runtime pip/model download. The supplied Dell Precision 7780/32 GB/RTX 2000 Ada 8 GB is a target assumption, not measured hardware. Starting limits: ranker 1 CPU/1 GiB, trainer 2 CPUs/2 GiB with BLAS thread limits; tune from measured pilot data. These are operational limits, not evidence of model quality.

First determine whether Express remains on the host or is containerized in the actual deployment. A host API can reach an explicitly loopback-published ranker port; a containerized API uses a private network name. Do not change PostgreSQL/MinIO layout solely for this feature. Provision approved image digests, pinned dependency lock/wheelhouse, checksums, schema and fixture artifacts online before deploying offline. Record image/platform compatibility and disable network downloads/telemetry in serving/training. Smoke-test with external egress denied after provisioning. Startup order alone does not imply service readiness ([Docker Compose readiness guidance](https://docs.docker.com/compose/how-tos/startup-order/)); WFC must have no required dependency on ranker health.

Artifact root (proposed dedicated volume, not a production path claim): `exports/<scope>/<version>/`, `indexes/<scope>/<generation>/`, `models/<scope>/<release>/`, `manifests/active.json`, `manifests/disqualified.json`, `jobs/`. WFC owns scoped exports; ranker reads only granted export/index/model partitions, trainer writes staged models/job output; database and MinIO credentials are absent. Authenticate internal calls with narrowly scoped local service credentials and request-bound scope grants; don't publish the ranker API to the general network.

Persist checksums, normalization version, reviewed dependencies and evaluation reports with artifacts. Never load an untrusted serialized model. Backup WFC review/template/identity records together with artifact manifests and current permission/tombstone journal; protect artifacts as project data. Restore validates compatibility and reapplies disqualifications before enabling the service. Retain at least the active and previous compatible qualified release; actual retention horizon and export cleanup policy are deployment inputs. If no valid restored model/index exists, WFC deterministic fallback works.
