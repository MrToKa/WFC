## Existing modules and preservation requirements

Reuse `server/services/materialCapabilities.ts:20`, `MATERIAL_CAPABILITIES`, and the seven existing catalogs/composition tables. `MaterialKey` is category plus UUID, not a name or an unqualified UUID. The existing child-catalog mapping is authoritative: tray/support compositions currently choose cable installation materials; instrument owners choose instrument installation materials. Do not create a competing catalog or silently permit cross-catalog children.

Preserve `server/services/standardMaterialService.ts:267`, `expandStandardMaterialsFromAssignments`, including multiplicative paths and path-local cycle detection. Preserve owner/reference FK protection, duplicate-edge checks and supported units. Add occurrence information before `aggregateExpandedStandardMaterials` (`:160`) loses it. Separate branches may legitimately contain the same material; one physical allocation must not be counted twice. Existing aggregate edge uniqueness remains; new role/position allocations belong in a sidecar, not duplicate legacy edges.

`server/services/projectCableTypeSnapshotService.ts:5` copies expanded defaults and source provenance. Its replacement path deletes inherited defaults only (`:11`); manual defaults must survive. Do not re-expand already-expanded project defaults. Preserve current copied display, unit and quantity fields while adding explicit current identity and original lineage separately.

`server/routes/cablesRoutes.ts:1903`, `buildCableReportSummary`, uses current rows or virtual defaults. Its `pcs/m` rate is multiplied by design length once (`:1819`); fixed quantities stay fixed. `server/services/changeOrderService.ts:63`, `calculateInheritedChangeOrderQuantities`, treats a cable-type line as one cable: fixed companions are per line, rate companions follow length. Other parents multiply parent quantities. `calculateMinimumOrder` (`:105`) computes commercial package counts separately. Preserve these boundaries and 3-decimal cable-report rounding (`server/routes/cablesRoutes.ts:1720`). Role satisfaction never uses packaging quantities.

Two prerequisites prevent treating existing reads as immutable:

- Cable details GET (`server/routes/cablesRoutes.ts:2720`) calls `ensureCableMaterialsInitialized` (`:2755`), which may delete/insert component rows and change flags. New previews and revision readers must use pure projection logic.
- `getChangeOrder` (`server/services/changeOrderService.ts:305`) calls `synchronizeChangeOrderMaterialOrdering` (`:330`), refreshing commercial values from the live catalog. Existing detail/export reads are not fully frozen. Preserve already stored values; do not claim historical immutability until the supported read paths stop refreshing them implicitly.

Cable version records (`server/models/cableVersion.ts:6`) contain cable fields, not complete assembly snapshots. They cannot serve as review revisions.

## Migration, identity resolution and failure behavior

Prepare versioned, additive, transaction-bounded migrations with preflight counts and a ledger. Avoid appending unattended backfills to startup. A dry-run report is an artifact, not a migration. Any later authorized application must first verify target identity, backup/restore procedure and expected baseline counts.

Map concrete stable FKs directly where they identify the current selection. Preserve `source_master_material_id` and source assignment IDs as origin evidence. A legacy default PATCH can change its name without updating origin (`server/routes/cableTypesRoutes.ts:1263`); do not assume origin is the current material. Name matching may produce steward-review proposals within the correct catalog only. Ambiguous, renamed, missing or conflicting mappings remain nullable/unresolved. No fuzzy merge, row deletion or automatic approval.

Create legacy template revision zero as unreviewed with recorded lineage. Existing project/cable/Change Order copies retain stored values and IDs. Do not attach the newest template to historical copies whose revision is unknown. Old component rows start unallocated unless trustworthy evidence establishes role and position; historical quantities alone cannot establish allocation.

For inherited overrides retain original source and an explicit current override state. Current cable PATCH preserves the default FK while setting only a global customized flag (`server/routes/cablesRoutes.ts:3077`, `:3106`); explicit sync can align it back to default (`:1601`). Stage 1 must characterize this and ensure protected recommendation-linked revisions cannot be overwritten silently. Cable-type changes currently reset all cable materials (`:2603`); any protected change needs an explicit revision transition and visible consequences.

Migration failures roll back the current transaction or resume through the ledger; leave the feature disabled. Validate counts, identity coverage, unresolved mappings, copied units/values, lineage and reports on authorized disposable data before any rollout. Do not use destructive rollback that deletes newly authored review history; prefer tested restore or forward repair. Under the current instruction, all such database execution remains deferred.

## Authorization and consistency decisions

Catalog/template mutation is distinct from project assembly mutation. Existing catalog/default edits require admin (`server/routes/standardMaterialRoutes.ts:55`, `server/routes/cableTypesRoutes.ts:1129`); cable component writes require authentication (`server/routes/cablesRoutes.ts:2864`). Existing project lookup proves object-to-project ownership, not user membership. Do not infer a tenant ACL or grant engineering review to every logged-in user.

Record whether deployment intentionally permits all authenticated users to access projects or requires membership. Until selected, restricted-scope rollout and evidence export are blocked. Reviewer/domain-approver assignments must be explicitly configured; absent grants deny review/rule approval. Current admin checking can support catalog/template writes, but these capabilities remain separate from project writes and review authority.

Saving a project snapshot into a broader shared template scope additionally requires the design's source-to-destination `scope:publish-template` permission. Source read plus shared template write does not authorize disclosure of project components/context. Deny widening until configured, or retain the original restricted scope. Add a scope-widening denial test alongside S11/S21. Follow the design's explicit success schemas for every operation, including review/event versions, committed receipts, evidence generations and scoped export handles.

Follow design §6 mutation envelopes: expected assembly/review/template revision as applicable, catalog/rules/feature versions, and idempotency key. Scope is derived by the backend. Persist canonical request hash and receipt atomically with revision and event changes. Lock/recheck before validation; do not trust a client deficit, candidate approval or displayed score. A distinct concurrent request loses with a revision conflict. Graph edits use consistent graph locks so simultaneous cross-links cannot each pass a stale cycle test. Transaction presence alone is insufficient.

## Remaining inputs and acceptance gate

Foundations may use clearly marked synthetic fixtures. Production enabling requires verified subtype/current identity mappings; manufacturer/application evidence for fastener thread/geometry/material and whole-assembly limits; cable-marker fit/mounting/environment/marking requirements; role applicability, positions, quantity basis and rounding; named reviewers and project/evidence scope policy. Blank real values in design §10 remain blank. None is a routine inferred default.

Stage 1 acceptance requires:

- Stable category-aware identity with enforced concrete references and an honest unresolved backfill report; existing IDs/data preserved.
- Typed metadata/rule revisions with unknown states and provenance; unreviewed legacy data cannot enable rules or become training labels.
- Passing synthetic role, quantity, occurrence and allocation cases; fixed/rate/packaging boundaries characterized.
- Immutable assembly/template/review contracts, explicit lineage and overrides, scoped tombstones and one normalization version; no implicit review or template propagation.
- Pure new preview/historical readers and coherent revision handling across supported mutations before new writes can be enabled; historical refresh conflict explicitly addressed.
- Separate project/catalog/reviewer permissions and transactional idempotency/preconditions, with unavailable SQL validation clearly documented.
- Reviewable migration artifacts, relevant checks reported, feature disabled, and **no database changes** under the present authorization. Report implementation completion separately from rollout and real-data readiness.

Out of scope: Python/FastAPI ranker, similarity index implementation, scheduled trainer, model fitting/evaluation/promotion, Docker changes, production data approval/backfill execution, global cross-project pooling, unsupported category rules, and full recommendations UI rollout. Later stages inherit S18–S22 and cannot activate models without independent evidence and predefined promotion gates.
